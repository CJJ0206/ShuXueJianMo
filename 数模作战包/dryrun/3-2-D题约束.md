## 一、结论：漏读自查**有效**，且量很大

乙清单抓到甲清单没有的 **11 条**，全部是真约束：

| 乙编号 | 漏掉的约束 | 为什么重要 |
|---|---|---|
| C05 | 出入口是红点、且 出入口 ⊆ 节点集 | 逃生终点合法性判据，我完全没登记 |
| C21 | "即刻监控到突水情况" ⇒ 监控延迟 = 0 | 决定工人何时开始获得信息，与 C17 的 1 min 通知是两件事 |
| C34 | 问题 3 须建**双源新模型**，不能把问题 1 结果线性相加 | 直接影响问题 3 是否被判"照抄问题 1"，是失分重灾区 |
| C39 | 问题 4 须以问题 2 方案为**对照基线**并说明改动 | 交付物要多一列"原方案"，我漏了 |
| C43 | 提交物总计 **8 个 xlsx**，命名互不可换 | 我只逐条写了文件名，没有"总数 == 8"这条可执行断言 |
| C44 | 须原样读取，**不得重映射节点 ID** | 重编号会让结果表对不上模板行 |
| C46 | 邻接巷道须按 Δz **显式三分类**（水平/下行/上行），上行不分流 | 我只写了"向水平与下行分流"，漏了它的对偶结论"上行不得进水" |
| C47 | 逃生路径须以**节点有序序列**呈现，不能只给一个时间值 | 交付形态约束 |
| C48 | 附件 1/2 结果**不得混排** | 跨网络污染是批量求解时最常见的低级错误 |
| C18 | "保留 2 位小数，**下同**"覆盖四问全域含正文 | 我的 C11 只约束了结果文件 |
| C20 | "巷道最高点"可读作端点较大 z，**或** 断面上缘 (max z + 3 m) | **我完全没意识到的歧义**；两种读法使全部充满水时刻相差一段体积对应时长，进而翻盘"何时无水可走" |

乙清单自评"最容易漏的三类"是：交付物格式类、术语定义与判据类、边界与阈值归属类。
**实测它自己的漏项预测与真实 diff 高度吻合** —— 这个机制不仅有效，还能自我评估。

## 二、甲清单独有的 10 条：全部来自模板，题面一个字没提

C33–C42 是乙清单**不可能**抓到的，因为它们不在题面里：

| 编号 | 只存在于模板的约束 |
|---|---|
| C33 | result1/3 每个文件是**两个 sheet**，名称逐字为"端点水流到达时刻""巷道水流充满时刻" |
| C34/C35 | 必须填满 **663 个端点 + 977 条巷道**，行数可实测核对 |
| C36 | 附件表是**双行表头 + 合并单元格**，`pd.read_excel` 默认读法直接把表头读成数据 |
| C37 | result2/4 是**三个 sheet**，逐字名"工人1逃生路径"… |
| C38 | 六列列序：序号 / x / y / z / 到达时刻 / 巷道编号 |
| C39 | **序号从 0 起**，第 0 行预填矿工坐标、到达时刻 = 1（即通知时刻） |
| C40 | 结果表时刻单位是**分钟**，而题面速度是 **m/s** |
| C41 | 第 0 行"巷道编号"为空 ⇒ 该列语义（离点所走 or 到点所经）不确定 |
| C42 | 模板未规定"水永不到达"怎么填（留空 / 无穷 / -1） |

### 由此得出 R5：`卡 1-1` 的输入定义是错的
卡片原文 `输入：{题面全文}、{已抽清单}`。**只喂题面，42 条里会有 10 条永远抽不到，
占 24%。**明天真实赛题同样带模板，这 24% 恰好是最容易在 V3-5/V1 被判不合规的一类。

→ 改为：`输入：{题面全文} + {附件与结果模板的结构实测：文件名、sheet 名逐字、表头行结构、
行列数、预填单元格值、列名内嵌单位}`，并要求先跑 `卡 1-5 附件数据体检` 再跑 `卡 1-1`
（两卡顺序在 spec §8.4 里原本是解析在前、体检在附件到手后并行，需调整）。

## 三、由乙清单反推出 gold card 的一处表述错误（R6）

乙在回报里专门提醒：*"卡片要求'严格六字段'但字段模板实为 7 段，我按模板逐项输出，未删字段。"*

它是对的。gold card 写的是
`C编号|"题面原文逐字引用"|你的解读|H或S|单位|建议验收断言|所属小问`
= ID + 6 个字段 = **7 段**，而 prompt 正文说"严格六字段"。
这种措辞不一致的后果不是报错，而是**某个会话真的去数成六段、把最后一个字段吃掉**，
然后 `schema.parse` 在第 37 行抛"需 6 字段，实为 5"，现场还得反过来猜为什么。

→ gold card 与 `卡 1-1` 措辞改为：「除 ID 外六个字段，连 ID 共 7 段，竖线分隔」。

## 四、附带压出的 schema 缺陷（R7，已改代码）

第一次把甲清单写进 `SPEC.md` 时，V1 直接判红：
`[V1 FAIL] SPEC.md 行格式: SPEC.md:37 需 6 字段，实为 11`

根因：我用 `|` 作字段分隔符，但**表头名本身就含竖线**（C36/C38 要引用 "端点编号|端点坐标|…"）。
这不是夹具的偶然——明天引用 Excel 列名、数学区间、公式时同样会带竖线。

→ `schema.py` 现支持 `\|` 转义（切分时只在未转义竖线处切，读入后还原），
报错信息追加"字段内含竖线须写成反斜杠转义"；补 2 条单测（转义还原、未转义时给可操作提示）。
**这条是"用了自己定的协议一次"才发现的，坐在键盘前想不出来。**
