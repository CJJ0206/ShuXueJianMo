## 一、代码与规范缺陷（已修，附证据）

### D1 `subprocess` 在中文 Windows 上按 GBK 解码，`run_all.py` 必崩 —— 严重
- **现象**：`test_run_all_空壳verify返回非零` 报 `TypeError: 'NoneType' object is not subscriptable`；
  完整栈显示 reader 线程 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xab`。
- **根因**：`subprocess.run(text=True)` 在中文 Windows 用本地码页解码子进程输出；
  子进程打中文即抛异常，`r.stdout` 变成 `None`。
- **为什么明天会炸**：`run_all.py` 是 V0-3 与 V2 的执行入口，每天要跑几十次，
  而我们的脚本按规矩全用中文输出。**会在明天最累的时候以最难认的形式崩。**
- **处置**：`run_all.py`/`env_lock.py` 显式 `encoding="utf-8", errors="replace"`；
  `stdout/stderr` 用 `(so or "")` 兜底；补 `subprocess.TimeoutExpired` 分支（原来超时会直接抛出未捕获异常）。
- **回归测试**：`test_run_all_子进程打中文不崩`（植入中文输出并断言退出码如实传回）。

### D2 `numbers_add.py` / `issue_add.py` 的 CLI 参数计数 off-by-one —— 中
- **现象**：正例被当用法错误拒绝（只打印 docstring，exit 1）。
- **更糟的是**：负例（缺复现命令）当时"exit=1 符合预期"**其实是走了错分支**——
  典型的假绿，测试看着过了，实际什么都没验。
- **根因**：`len(argv) < 8` 应为 `< 7`（prog + root + 5 字段）。
- **处置**：修正计数；把退出码语义定死并在 `main()` 内决定：
  `0` 成功、`1` 违反判据被拒、`2` 用法错误。**原来 try/except 在 `__main__` 里，
  直接调用 `main()` 的测试会绕过异常处理**，一并修掉。
- **回归测试**：新增 4 条 CLI 测试（正例返回 0、缺复现命令返回 1 而非 2、参数不足返回 2）。

### D3 计划里的 `test_干净工作区通过` 前提是错的 —— 中
- **现象**：`bootstrap.py` 生成的模板自带 4 个空 `##` 小节与未填的 `handoff.md`，按 V1 语义**必须判红**。
- **根因**：我把"刚生成的空壳"当成了"干净"，恰好颠倒了 V1 的用途。
- **处置**：测试改为两条——`test_空白工作区必须判红`（更强的敏感性证明）与
  `test_填齐后通过`。实测 V1 对 B 夹具：体检后判红 2 项（`SPEC.md 无约束条目`、`handoff 未填`），
  补齐后 `PASS`。

### D4 spec §8.2 拥挤度加权式漏了符号反向处理 —— 严重（由 T2 子代理发现）
- **根因**：S3（数据摩擦）与 S5（工作量天花板）的定义是"越高越冷"，
  原式 `1.2×S3 + 0.8×S5` 正号相加，会把最该判冷的题算成 crowd 最高。
- **危害**：排序整体反转，且**表面完全自洽**——明天会系统性地把选题推向
  "看起来热、其实做不动"的方向，没有人会怀疑一个算得很顺的公式。
- **处置**：改为 `crowd = (1.5S1 + 1.2S2 + 1.2(6−S3) + 1.0S4 + 0.8(6−S5)) / 5.7`，
  并把 S2 的千字刻度写死。记入 spec §13 第 7 条。

### D5 求解代码把物理关系写反了方向 —— 严重（今晚最有教学价值的一条）
- **现象**：`3-6-厚度.py` 给出厚度 6.9×10⁹ nm。
- **两层错误，且互相掩盖**：
  ① 干涉项 `cos(2π·2nd·ν̃)` ⇒ 条纹频率 `f = 2nd`、厚度 `d = f/(2n)`；我写成 `d = 1/(2nf)`。
  ② 原反射率谱被缓慢趋势（SiC Reststrahlen 宽吸收带）主导，最强谱峰落在 bin=1，
     根本不是条纹。**若只犯 ①，bin=1 会算出 0.54 μm——一个看起来完全合理的数。**
- **这才是重点**：两个错误单独存在时，有一个会让另一个变得不可见。

## 二、对验收规范本身的修订（今晚实测逼出来的，不是想出来的）

### R1 V2-1"两路一致即通过"不充分 —— 必须补一条修订 spec 的判断
第一次跑双路：A 路选 bin=1、B 路选 ≈0，**两者都错，却"只差 1.00 bin"，判 PASS**。
即：**共享同一错误假设的两条实现会漂亮地互相印证。**独立复算防得住"写错"，防不住"想错"。

据此，`卡 3-2 自证包` 的通过条件从"一致"改为**四条同时成立**：

1. **双路一致**（必要，非充分）；
2. **结果落在独立给出的粗估区间内** —— 区间必须在看到任何求解结果之前写下（卡 2-2）。
   今晚这条正是靠"外延层 1–15 μm"的先验才把 bin=1 的荒谬选择暴露出来；
3. **合成锚点取回已知值** —— 喂一段答案已知的合成信号给同一段估计代码（V2-3 的正确形态）。
   今晚实测：真厚度 1.5/3.0/8.0 μm 复得 1.60/3.21/8.01 μm，方向与量级都对；
4. **两路不得共享被检验的那个假设** —— A 靠去包络排除慢趋势，B 就必须用**不同机理**
   （限制搜索带）。机理一不同，差异立刻显形：双路差 **2.98 bin → FAIL**。

### R2 新增判据：最优解落在搜索区间端点即无效
B 路最终 `f=0.000562` 正好压在先验带下边界（bin=2 = `ceil(lo/res)`）。
**撞边说明真正的最优在界外**，此时"在界内找到了最优"毫无意义。
→ 写进 `卡 3-1` 与 `卡 3-2`：任何带界搜索（频率带、参数域、超参网格、箱约束优化）
都必须检查 argmin/argmax 是否落在边界，落界即判无效并扩界重算。
今晚这条是实测撞出来的，不是预防性写的。

### R3 耗时估算必须先 warmup
`3-5-冒烟.py` 冷启动测得 19.3 ms/次，warmup 30 次后稳态 **2.83 ms/次**，差 6.8 倍。
→ 写进 `卡 0-3` 的"算力与时间爆雷"判据：**按稳态估，且计时须 `torch.cuda.synchronize()`**。
不写这条，明天可能因为一次冷启动计时而错误回避视频/深度学习类题。

### R4 `卡 2-3 单位坐标系` 增加强制核对项
数据体检实测：波数列名写 `cm-1`，但**标称步长 0.4822、实际步长 0.481000~0.483000
（std 3.3e-4，相对抖动 0.4%）——网格非等间隔**。所有假定等间隔的算法（`rfft`、
`correlate` 的延迟换算）在此数据上都有系统偏差。
→ 卡 2-3 必须要求："**单位与步长都要从数据实测验证，不能只信列名与题面正文**"。
